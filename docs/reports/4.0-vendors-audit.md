## FORM AND VALIDATION TABLE (step A4)

`views/dashboard/vendors/create.php` and `edit.php` have the same four inputs (plus CSRF hidden input). Both forms carry `novalidate`.

| Input name | Type | maxlength / attrs | Controller read & validation (`collectInput()`, lines 228-291) |
|---|---|---|---|
| store_id | select (`form-select`) | no maxlength; `required` attribute (ineffective under novalidate); empty "Select store" option | `Validator::integer($rawStoreId, 1)` → 'Store is required.'; then `storeModel->findById()` → 'Selected store does not exist.' |
| name | text | maxlength 255; `required` attribute | `Validator::sanitize($rawName, 255)`; empty → 'Vendor name is required.' |
| slug | text | maxlength 255; create placeholder "leave-empty-to-generate" | `generateSlug($rawSlug)`, falls back to `generateSlug($name)`; empty → 'Vendor slug is required.'; `vendorModel->slugExists()` → 'Slug is already in use.' |
| rating | number | `step="0.01" min="0" max="5"`, placeholder "Rating (0-5)"; no maxlength | empty → NULL; `is_numeric($rawRating)` else 'Rating must be a number.'; `(float)` cast; `< 0 || > 5` → 'Rating must be between 0 and 5.' |

`update()` additionally refuses a store change when `offerModel->countByVendorId($id) > 0` ('Cannot change the store of a vendor that already has offers.', lines 166-168). `delete()` refuses deletion when the vendor has offers (lines 210-214).

**Rating comma finding (facts only):** the controller uses PHP `is_numeric()` and `(float)` — `is_numeric('4,5')` is `false`, so a comma decimal throws 'Rating must be a number.'; `is_numeric('4.5')` is `true`, it becomes float `4.5` and is stored in `vendors.rating decimal(3,2)`. The edit view prints the raw database value via `htmlspecialchars((string) $ratingValue)` with no `number_format` or comma replacement, so a DB value of `5.00` displays as `5.00`; any value displayed as `5,00` would be rejected on resubmit. The input is `type="number"`, which browsers normally submit with a dot decimal.

**Store dropdown data:** `AdminVendorController::create()` line 57 and `edit()` line 119 call `$this->storeModel->findAll('name ASC')` and pass it as `'stores'` to the view (also reloaded in both catch blocks, lines 90 and 174). The views loop `foreach ($stores as $store)`, print `value="<?= (int) $store['id'] ?>"` and the escaped `store_name`, and compute `$storeOptionSelected` from `$old['store_id']`. A Location dropdown could follow the identical pattern with a `LocationModel`.

**Dashboard vendors list:** `views/dashboard/vendors/index.php` columns are ID, Vendor Name, Platform, Rating, Status, Actions (lines 42-47). There is no search box, no filter and no pagination — `AdminVendorController::index()` simply calls `findAllWithStore()`. A Location column and a location filter would fit into this list using the same pattern as the products list's status filter.

## IMPORTER IMPACT (step A7)

`ProductImporter` DOES create vendors. It reads `vendor_slug`, `vendor_name` and `marketplace` from the CSV (lines 178, 188) and, when `vendor_slug` is empty but `vendor_name` is present, generates `marketplace-vendor` as a slug and calls `insertVendor($storeId, $vendorNameValue, $generatedVendorSlug, $storeRatingValue)` at line 415; `store_rating` comes from the CSV column. `insertVendor()` (lines 954-968) INSERTs only `store_id`, `name`, `slug`, `status` ('active') and optionally `store_rating`. The dashboard import help (`views/dashboard/products/import.php:231-232`) claims vendors are never created, which is stale (also noted in WORKLOG.md:232).

New nullable `vendors.location_id` and `vendors.description` columns would not break the importer's explicit INSERT column lists (unlisted columns take their defaults), but the importer would never populate them, so imported sellers would have empty location/description. If either new column were NOT NULL without a default, `insertVendor()` would fail. The CSV schema and import help would need a decision if location/description should be importable.
